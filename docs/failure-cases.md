# 真实维护案例：错误怎样改变了系统设计
版本：公开审稿草案 v0.1；依据历史记录，部分修复的**当前状态待验证**。

## 案例 A：报告形式合格，却不具备正式分析资格

**问题：** 历史模拟报告中的固定栏目齐全，结构检查显示通过；但多个数据模块缺少同日可验证资料，只能写 `REFERENCE_ONLY`、`DETAIL_REQUIRED`。

**潜在风险：** 使用者可能把“结构完整”误解成“市场分析准确”，进一步把参考性结论当作实际执行依据。

**设计回应：** 我逐渐引入固定的 **21 项输出合同**，规定正式分析应按栏目逐项填写，发现遗漏要先补全再输出。同时必须将栏目存在性与数据质量拆开：格式合同不能绕过日期、来源和关键字段的检查；数据不足时要显示缺口，不能生成无依据的正式结论。21 项合同可减少报告内容遗漏，却不能证明模型完全执行所有分析纪律。

**验证现状：** 有历史诊断文件和部分脚本可供审阅，但公开演示用的自动化测试尚未制作；不得称为已经完成全面修复。

## 案例 B：历史状态被继承为“今天”的事实

**问题：** 持续运行的 Agent 容易用昨天的报告、旧截图或缓存覆盖用户最新确认的数据。

**设计回应：** 为输入附上来源和业务日期；优先使用最新的已确认事实；旧状态可以作为参考但不能自动晋升为当前事实。

**可迁移性：** 同样适用于库存、设备监控、客户工单和长期写作设定的版本继承。

**验证现状：** 本地规则和数据包中已看到限制定义；当前完整端到端行为待测试。

## 案例 C：定时任务越过数据准备与用户授权

**问题：** 让 Cron 直接执行长篇报告，在缺资料时可能形成错误结果、超时或成本浪费；开启监控或外部发送也可能越权。

**设计回应：** 定时任务先调用确定性数据门禁；只有满足要求并得到用户请求，才进入正式报告。提醒、观察、分析和实际动作分开授权。

**验证现状：** 2026 年历史文件记录了冻结、模拟验证和后来更改调度链的过程；尚未确认本次审稿时的生产调度状态。

## 对 AI 工程最重要的教训

- 不把 AI 的自信语气当作事实质量。
- “程序能运行”与“输出可信”是两个测试维度。
- 版本回退与变更日志必须保留。
- 用户提出的禁止行为，应尽量落实为可测试的条件。
- 对复杂系统，公开失败经历比只展示架构图更有用。
